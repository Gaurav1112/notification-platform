## 1. What this is

An enterprise notification platform — SMS, email and push — designed for 50M users and millions of
sends a day. Java 17, Spring Boot 4.1.1, Kafka 4.3.1 (KRaft), PostgreSQL 18.6, Valkey 9.1.1.
Eleven Maven modules, three deployable applications. Providers are mocked on purpose
([ADR-005](adr/ADR-005-mock-providers.md)); there are no vendor credentials anywhere.

It is a portfolio project. It is not deployed and has no users.

## 2. The thing that will waste your afternoon if you skip it

**You must run all three applications.** Not one.

| Process | Port | Owns |
|---|---|---|
| `app-api` | 9080 | Accept, idempotency, queries, **Flyway** |
| `app-worker` | 9082 | Dispatch consumers, provider calls, retry routing |
| `app-scheduler` | 9081 | **Outbox sweeper**, due-scan, lease reaper, partition maintenance |

The API commits a notification row and an outbox row in one transaction, then tries a best-effort
publish. The **scheduler** owns the sweeper that actually drains the outbox. Start only the API and
every request returns `202` and then sits at `PENDING` for ever. That looks like a hung platform and
is really a missing process.

```bash
docker compose -f docker/compose.yml up -d
./mvnw -o -q install -DskipTests            # see §3 — this step is not optional
./mvnw -o -q -pl app-api       spring-boot:run -Dspring-boot.run.arguments=--server.port=9080 &
./mvnw -o -q -pl app-worker    spring-boot:run -Dspring-boot.run.arguments=--server.port=9082 &
./mvnw -o -q -pl app-scheduler spring-boot:run -Dspring-boot.run.arguments=--server.port=9081 &
```

Then: <http://localhost:9080/swagger-ui/index.html>

## 3. Local-development traps, each of which cost real time

- **`spring-boot:run -pl <module>` resolves sibling modules from `~/.m2`, not from `target/classes`.**
  After editing a `platform-*` module, `mvn compile` is not enough — the running app still loads the
  stale installed jar. Run `./mvnw install -DskipTests` or your change silently does not exist.
- **`pkill -f "spring-boot:run"` kills Maven, not the app.** It forks a JVM. Kill
  `-f "MavenWrapperMain"` and `-f "TieredStopAtLevel=1 -cp"`.
- **Never `lsof -ti:PORT | xargs kill -9`** on this machine. It has twice taken down Rancher
  Desktop's VM, which kills Postgres, Kafka and Valkey with it. Recover with `rdctl start`.
- **Flyway history lives in the `notif` schema**, not `public`. To reset: `DROP SCHEMA notif CASCADE`.
- **`db/local` is on the Flyway path only under the `local` profile**, and only `app-api` runs
  Flyway. `V900` seeds the development tenant, `V901` seeds the five mock providers.
- **BSD `sed` has no `\b`**, and `awk` rejects multi-line strings. Bulk edits with either can exit 0
  having changed nothing. Use Python, and *check the result rather than the exit code*.

## 5. What is NOT done — the actual backlog

Ordered by how much it matters. [`STATUS.md`](STATUS.md) has the long form of each.

1. **Inline `content` is accepted and then dead-lettered.** `SendNotificationRequest` validates
   "exactly one of `template` or `content`", so inline content is a documented, accepted input — but
   `NotificationRequestedEvent` carries no content field, so `EchoTemplateRenderer` throws
   `no templateCode on the request` at fan-out and the record goes to the DLQ. **This loses work
   that the API said it accepted**, which makes it the most serious open defect. Until fixed, only
   `template` payloads work end to end. Confirmed still failing on 2026-08-31.
2. **`ProviderHealthGate` does not fire on a health-only outage.** It tests
   `allCircuitsOpen(channel)`, but a provider excluded by `isHealthy()` is never called, so its
   breaker stays CLOSED. The router excludes on **health**; the gate keys on **circuit state**. With
   both email providers `HARD_DOWN` the worker logs `no eligible provider` on every record while
   `notification.dispatch.gated` stays `0.0` — in the exact outage the gate exists for, it does not
   engage. Fix: treat a provider as unavailable when it is open **or** unhealthy.
3. **The webhook round trip has never been exercised**, so `DELIVERED` and `BOUNCED` from a provider
   callback are unobserved. `SENT` is as far as the template path has been watched go.
4. **Deduplication is a single-JVM `HashMap`.** Idempotency breaks at two worker pods. Needs the
   Valkey-backed implementation.
5. **`RateLimitedProvider` and `TracedProvider` are pass-throughs.** `CircuitBreakerProvider` was one
   too and is now real — use it as the template.
6. **Tenant scoping is nearly complete but was finished under time pressure.** Re-audit repository
   methods for a missing `tenantId` predicate; `findByRequest` was a cross-tenant *write* hazard
   before it was closed.
7. Preferences, templates and suppression are stand-ins. Aggregate counters are not maintained.

## 6. Design decisions you should not accidentally undo

Each of these looks like an inefficiency until you know why.

- **Traffic classes are physically separate Kafka topics**, not a priority field. A partition is
  strictly FIFO, so a priority field is a lie: 9M bulk messages at 200/s is 12.5 hours of head-of-line
  blocking in front of a password reset.
- **`DELIVERED` (rank 80) is deliberately not terminal.** An SMTP 250 means "queued"; a hard bounce
  legitimately arrives minutes later. A state machine that treats `DELIVERED` as final drops the
  bounce, the address never reaches suppression, and sender reputation degrades for every tenant on
  the IP pool.
- **`CANCELLED` (28) ranks below `QUEUED` (30)** so "you cannot cancel something already queued" is a
  data invariant rather than an `if`. Zero rows returned is a normal outcome, not an error.
- **The attempt row is committed *before* the provider call.** Write it afterwards and a crash
  between send and write is indistinguishable from never having sent.
- **SMS is at-most-once; email and push are at-least-once.** Twilio has no client-reference field, so
  an indeterminate SMS cannot be reconciled afterwards. Retrying is how a user gets three passcodes.
- **Outbox rows are `DELETE`d, never marked published**, so the table cannot grow without bound.
- **No index on `notification.status`.** It would forfeit HOT updates — roughly 4 GB/day of extra WAL.
- **`ProviderIds` throws on a missing row rather than defaulting.** Defaulting would attribute
  attempts to the wrong vendor and corrupt every cost and health rollup. This is what made §7's bug
  findable.
- **Chaos state is per-process and stays that way.** A shared store would claim a blast radius the
  real system does not have.

## 7. The bug worth understanding before you touch anything

`notif.provider` was empty. `V1` creates the table and seeds no rows. The five mock adapters are
Spring beans, so `ProviderRegistry` found them all and `/v1/providers/health` reported every circuit
CLOSED and healthy — while **not one message was ever delivered**. 177 dead letters, zero
`delivery_attempt` rows.

It hid because every layer reported success in its own terms: `202` on accept, rows advancing to
`QUEUED`, all circuits CLOSED. That last signal is the instructive one — **a circuit breaker only
records calls that happen**, so zero calls is indistinguishable from zero failures. The one number
that gave it away was `p95LatencyMs: 0.0` on every provider: a provider that has merely never been
*slow* still records a latency once it has been called at all.

Two related defects had the same root cause — process-local state exposed by the wrong process. The
chaos and provider-health endpoints both lived in `app-api`, which routes no traffic, while the
state they describe is written by the worker. Both now live in `platform-provider`.

**The transferable lesson: a green test suite and a healthy-looking status page can coexist with a
platform that delivers nothing. Verify against the artefact, not the exit code.**

## 9. If you pick this up next

The highest-value next commit is **§5.1, inline `content`** — it is the only open item that loses
work the API promised to do, and the fix is bounded: add the content fields to
`NotificationRequestedEvent`, teach `EchoTemplateRenderer` to use them when `templateCode` is absent,
and add a test that drives the inline path to a `delivery_attempt` row.

After that, **§5.2** is a few lines and closes a real hole in the outage response.

Before claiming anything new works: run it, look at the artefact, and only then write it down.
